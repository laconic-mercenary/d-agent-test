## 1. `external-recon-no-breach`

**設定:** 小さな会計事務所、Meridian Ledger。DMZにある公開ドキュメント
ポータル `WEB-01`。方針として、インターネットから到達可能なのはポート
80/443のみで、SSH管理アクセスは内部限定とされている。

**何が起きたか:** `203.0.113.77` が `WEB-01` に対して、一般的な21ポートを
対象にポートスキャンを実施(`2024-06-11T14:09:59Z`–`14:10:02Z`)。19ポートは
即座に拒否(ASA `106023`)。2ポートは実際のTCP接続が成立: ポート443は
データの送受信なしでほぼ即座にリセット(Zeekの `conn_state: RSTO`)。
ポート22はクリーンなTCPハンドシェイクが完了(`conn_state: SF`)し、SSHの
ログイン試行が1回行われる — ユーザー名は `unknown`、失敗し、接続は
`[preauth]` で閉じる。他のどのホストにもそれ以上の動きは一切ない —
攻撃者のIPを他のすべてのホストのログでgrepして確認済み、ヒットはゼロ。

**ひねり:** ポート443が到達可能なことは方針に合致するが、ポート22が
外部からの接続に応答していることは方針に**反する** — 方針上、SSHは
インターネットから到達可能であってはならない。何かが成功したかどうかに
関わらず、報告に値する実際の不一致である。意図的なおとりが `WEB-01` 自身の
syslogに存在する: 1時間以上後、*内部*IP(`10.30.20.10`、すなわち
`FILE-01`)から `svc_mgmt` という無関係なSSHログイン失敗がある —
単純な `grep "Failed password"` では両方にヒットする。Q3で正しく
引用すべきはどちらか一方だけ。

**設問(5問、100点):** スキャンの特徴づけ(20点) → どのポートが通過したか
+ その結果(25点) → SSH試行は成功したか、`conn_state` だけでなくホスト
レベルの証拠が必要(20点) → これは方針に合致するか、部分的な不一致が
期待される(15点) → 侵害の結論 + 適切な報告(20点)。

**既知の問題(影響なし):** `GROUND_TRUTH.md` は「拒否21件 + アラート
`733100`」と主張しているが、両方とも誤り — 実際は拒否19件+接続2件で、
`733100` はどこにも存在しない。採点には使用されていない。

本物のイベントを切り分けること; (2) ログ消去の実際の効果を、成功した
と仮定するのではなく検証すること。

**設問(5問、100点):** 6件のログオンのパターン + 共通の送信元(25点)→
正規の4648ノイズとの区別(20点)→ 認証プロトコルに関係なく、文書化された
ローカル限定の用途に基づいて、なぜ異常なのか(15点)→ ログ消去イベントの
配置(15点)→ 効果の検証 + 統合 + 調整された確信度(25点)。

**既知の問題:** データ面では問題なし; 2つの本物の*エンジンの挙動に関する
発見*がこのケースの設計を形作った(回避すべき不具合としてではなく):
`AuthenticationPackageName` はアカウントのスコープに関係なくランダムな
70/30の判定であり、`log_cleared` は純粋に追加的である — いずれもエンジンの
ソースコードとレンダリング結果の両方で直接確認済み。

## 9. `rdp-remote-file-write`

**設定:** 小さな専門職サービス事務所、Alderwood Partners。1人の
スタッフ(Dana Whitfield)、2台のワークステーション、ネットワークセンサー
なし、おとりなし — このセット全体の中で最も単純なケース。

**何が起きたか:** Danaは自分のワークステーション(`WS-01`、
`10.40.12.11`)から共有ワークステーション `WS-02` へRDP接続
(`14:40:48.99Z`、Type 10、`LogonId 0x7b0ebea`)、その2秒後に
`notepad.exe` をコマンドラインに `...Documents\team-notes.txt` を
指定して起動(`14:40:51.07Z`、`SubjectLogonId` が一致)。完全に無害。

**ひねり:** このケースは曖昧さではなく精度を中心に構築されている。
**この `.txt` ファイルに対するSysmonのFileCreateイベントはどこにも
存在しない** — 直接の再生成で確認済み — この環境のSysmon設定は、
怪しい場所にある実行ファイルに対してのみファイル作成を記録するため。
証明されているのはファイルパスを引数として起動されたプロセスであり、
「ファイルが書き込まれた」ことはそこからの合理的な推論であって、直接
証明された事実ではない — 直接証明されたと主張する答えは減点される。
別件として、アイデンティティのフィールドは、これがワークグループであり
ドメインではないにもかかわらず `ALDERWOODPARTNERS\dana.whitfield` として
レンダリングされる — 確認済みの、修正不可能なエンジンのレンダリング
バグである。これをアイデンティティの証拠として引用するのは正しいが、
実際のAD基盤やなりすましの証拠として扱うのは行き過ぎであり、このケースは
まさにそうした誤検知の罠を見つけることも試している。

**設問(6問、100点):** 2つの行動+順序、ファイル書き込みは適切に
留保される(15点)→ 行為者+証拠(15点)→ タイミング(15点)→
セッションの発生元ホスト/IP(15点)→ 紐づけとなるLogonId(15点)→
悪意ある活動についての結論、なし(25点)。

**既知の問題(影響なし、文書化済み、採点には使用されていない):**
`GROUND_TRUTH.md` の「Rdp_Session」行は、`data/` のどこにも対応する証拠が
ない時刻(`14:19:56Z`)を記載している — どのログファイルにも実際には
レンダリングされなかった、内部的な因果関係の前提条件のアーティファクト
である。

## 10. `rogue-service-account-privcreep`

**設定:** 小さなデータ分析コンサルティング会社、Summit Ridge
Analytics。`svc-reportgen` は、無人の夜間レポート作成ジョブという
1つの用途のためだけに文書化されている — 誰であれ、いつであれ、対話的な
使用は一切想定されていない。

**何が起きたか:** `svc-reportgen` に対する正規の4648イベントが全4ホストに
わたって22件(3ホストだけではない — `WS-NKOWALSKI-01` だけで9件)、
常に `SubjectUserName: SYSTEM`; プロセスはさまざまで、**信頼できる
判別要因ではない**(22件中9件は正規のものでも `powershell.exe` を
使用している)。そして1件だけがこのパターンを破る:
`2024-10-21T15:15:21Z`、`SubjectUserName: diego.velasquez`(実在の人間、
`SYSTEM` ではない)— このフィールドだけが唯一完全に信頼できる手がかり。
5分後: `Add-ADGroupMember -Identity 'Domain Admins' -Members
'svc-reportgen'`(`15:20:08Z`)、その後実際のグループメンバーシップ変更
である4728イベント(`15:20:23Z`)。

**ひねり:** *手がかり*は明示的クレデンシャル使用イベント自体
(Stage 2)であり、グループメンバーシップの変更(Stage 3)ではない —
サービスアカウントがそもそも対話的に使われたという事実自体が、その後
何が起きるかとは無関係に、すでに十分な異常の兆候である。グループ
メンバーシップの変更を「統制が最初に働くべき時点」とするような答えは、
順序が逆になっている — これがこのケースの中心的な、意図的に設計された
罠である。

**設問(5問、100点):** 通常のベースラインの特徴づけ、SYSTEMが唯一一貫
した手がかり(20点)→ そのパターンを破る1件、subjectであってprocessでは
ない(25点)→ エスカレーション、両方のイベント(20点)→ **核心** —
統制が最初に働くべき時点はQ2のイベントであり、グループ追加ではない
(15点)→ 完全な統合 + 権限変更の記述(20点)。

**既知の問題:** `GROUND_TRUTH.md` はDiegoのローカルログオンを誤記している
(このプロジェクトで繰り返し現れているこのテンプレート上のパターンの
6件目の確認例)。v1.1には2つの実際の解答キーの修正が含まれる: ベース
ラインの件数が過小に数えられていた(1ホスト分が完全に欠けていた)、また
以前の草案は `ProcessName` 単体が信頼できる判別要因だと誤って主張
していた — 実際には違う。

## 11. `ssh-shared-key-overlap`

**設定:** 小さな開発会社、Fernbridge Labs。3人の開発者が1台の共有Linux
アプリケーションサーバー `APP-SHARED-01` を利用している。ADもWindowsも
存在しない。

**何が起きたか:** 2時間の収集期間内に5件の本物のSSHセッション(以前の
解答キーの草案は3件しか記載しておらず、本物の2件が欠けていた。v1.2で
修正済み): Marcus自身の正規のセッション(`14:11:24Z`、自分のIP)→
Priyaの正規のセッション(`~14:15:11Z`、自分のIP)→ Gretaの正規のセッション
(`~14:18:27Z`、自分のIP)→ **2つ目の** `priya.desai` セッションが開く
(`~14:19:44Z`)、送信元は**MarcusのIP**で、Priyaの最初のセッションは
まだ開いている → Gretaの2つ目の、無関係なセッションが後で開く
(`15:54:37Z`)。発見事項: `priya.desai` が同時に2つの異なるIPから同じ
サーバーへセッションを持っている — 1人の人間には物理的に不可能。
syslog、eCAR、Zeekの `conn.json` という独立した複数のソースで裏付け済み。

**ひねり:** *別の*2つのセッション(Gretaの最初のセッションと、Marcus
自身の正規のセッション)がたまたまPriyaの両方のセッションと時間的に
重なっている — どちらも異常ではない; アカウントが異なり、それぞれ一貫した
単一のIPを持つ、ごく普通の職場での同時利用である。実際の異常は
具体的に「同一のアイデンティティが2つの送信元IPから」であって、
同時利用そのものではない。MarcusやGreta自身のアカウントを疑わしいと
するような答えは誤検知である。鍵が自発的に共有されたのか盗まれたのかは
意図的に未確定とされている — 結論をどちらか一方の説明として確定的に
主張してはならない。

**設問(7問、100点):** セッションの一覧、5件すべて(15点)→ 重複する
アイデンティティのセッションとその両方のIP(15点)→ 物理的不可能性と
その意味、事実として断定しない(15点)→ 独立した複数ソースでの裏付け
(15点)→ 他の重複セッション、正しく除外する(15点)→ 攻撃/マルウェアの
結論、なし(15点)→ ステークホルダー向け要約(10点)。

**既知の問題(影響なし、文書化済み、AUTの不利にはしない):**
レンダリングされたデータには、Priyaの2つのセッション間で一致する
SSH鍵フィンガープリントが含まれていない(前提は*共有された*鍵であり、
2か所で同一の鍵材料が見えるわけではない)— AUTがこれを見つけることは
期待しない。また、帰属に関する小さな現象: Marcusのワークステーション上に
`priya.desai.bash_history` というファイルが存在し、1件のSSHコマンドだけが
含まれている — 発見事項を補強するものであり、矛盾するものではない。

## 12. `websqli-webshell-pivot`

**設定:** 小さなEコマース小売業者、Solstice Outdoors。DMZにある公開の
注文照会アプリ `WEB-01`; 失効せずに残っている古いファイアウォール例外が、
DMZから内部サーバーへのポート445(SMB)通信を許可している。

**何が起きたか:** sqlmapによるスキャン、255件のリクエスト、
`15:00:23Z`–`15:12:23Z`、ステータスコードは混在(スキャン自身のリクエスト
のうち約59%が200を返す)。本物の侵害: `15:13:08Z`、手動による1件の
`UNION SELECT username,password_hash,... FROM admin_users` リクエスト
— **User-Agent**(`Mozilla/5.0`、sqlmapの署名ではない)と**ペイロードの
内容**(実際のテーブル/カラム名を指定しており、スキャンの一般的な境界
テストとは異なる)によって区別される; レスポンスサイズ(48,000バイト)は
信頼できる第3の手がかりではない — スキャンのレスポンスは700〜79,700
バイトの範囲に及ぶ。2分後に偵察(`whoami; id; uname -a; hostname`)。
`FILE-01` は24時間の収集期間全体でちょうど2件のSMB接続を受ける: 1件は
`DB-01` からの小さなもの(通常のバックアップ)、もう1件は偵察の2分13秒後、
`WEB-01` 自身から — 桁違いに大きく、SMBで接続する正当な理由が一切ない
ホストから。ファイアウォールはこれを一度もブロックしていない —
方針上許可されていた。

**ひねり:** `WEB-01` は踏み台であり、目的ではない — 本当に重大な出来事は
`FILE-01` へのピボットである。2つの判別テストが重なっている: HTTP 200は
侵害を意味しない(Q2); ピボット接続が重要な理由は「大きいから」ではなく
「存在する正当な理由がないから」(Q4)。無関係な背景ノイズの一致が
文書化されている(約13時間後の無関係な失敗SSHログイン)— これは2度目の
攻撃者の行動ではない。

**設問(5問、100点):** スキャンの特徴づけ(20点)→ 唯一の本物の侵害
リクエスト、2つ以上の手がかり(25点)→ 侵入後の偵察(15点)→ 2件のSMB
接続、正しく帰属させる(25点)→ 統合 + 具体的なファイアウォール例外の
解消提案(15点)。

**既知の問題(両方修正済み、現時点では問題なし):** v1.0では侵害の
タイムスタンプが10秒ずれており、スキャンの件数も誤っていた — いずれも
v1.1で修正済み。`ENVIRONMENT.md` は元々、セグメント間通信についての
ファイアウォール方針を唯一の根拠として過大に記述していた — 言い換え済み。
